# Build and retain review snapshots in CI

`python scripts/build_ci.py` runs the native export, writes static model shards in the same export process, builds the browser assets, and packages immutable snapshots. It uses the existing native exporter and packaging validators; it does not load the large unsharded JSON export back into memory.

The workflow in `.github/workflows/build.yml` is manual (`workflow_dispatch`). It is not a claim that this pipeline has run successfully, that the candidate renderer is accepted, or that the current source pins support every implemented adapter feature. The configured native pin must first include the reviewed renderer and transport changes. Dirty development checkouts deliberately fail publication validation.

## Local command

Install the Python client and npm dependencies from the same clean native checkout pinned in each selected `project.json`. Set `OPENSYSML_SOURCE` to that checkout and `OPENSYSML_BINARY` to its native executable. The executable must report the complete configured commit. The workflow builds it with `make build-sysml COMMIT=<full-commit>`.

```sh
export OPENSYSML_SOURCE=/path/to/pinned/OpenSysML
export OPENSYSML_BINARY="$OPENSYSML_SOURCE/bin/sysml"
python scripts/build_ci.py \
  --example examples/flashlight \
  --output build/site \
  --work build/ci
```

Repeat `--example` to build several declarative examples. Each directory supplies `project.json`, its model sources, and `story.md`; `story-draft.md` is the documented fallback. An explicit `story` property selects another filename. Prepared query tables and declared evidence are generated by the exporter under the intermediate `assets` directory.

Both the viewer and native renderer must be clean Git checkouts. All selected examples must use the exact native source pin that is checked out. Intermediate files should stay under ignored `build/` paths; creating output inside tracked source directories will make subsequent clean-source checks fail.

The Blue Dog example references a sibling checkout named `sv-blue-dog-editorial`. The manual workflow accepts an exact 40-character `DavidIngraham/sv-blue-dog` commit and checks it out at that path. It never substitutes a moving branch. Missing evidence or model paths fail export/assembly. Review IDs contain the example name, viewer commit prefix and a digest of exported source/tool provenance, so an independently changed model produces a different review ID.

## Existing history is an input

The separate `pages-history` branch holds the deployed static catalog and every immutable snapshot. Before adding new reviews, CI resolves that branch to a commit and checks out that exact commit. `--previous-site` verifies its snapshot manifests and copies its content into an empty output directory:

```sh
python scripts/build_ci.py \
  --example examples/flashlight \
  --previous-site /path/to/pages-history-checkout \
  --output build/site \
  --work build/ci
```

An unavailable remote is an error, not permission to start an empty catalog. A genuinely absent history branch permits the first build. Existing snapshot directories are retained. Packaging rejects a review ID that would identify different bytes and verifies content-addressed snapshot directories. The pipeline adds new reviews as **draft**; it does not automatically supersede an earlier review or declare engineering acceptance.

Publishing first commits the complete resulting static site back to `pages-history`, using a normal non-force push, then deploys the uploaded Pages artifact. A concurrent external branch update causes that push to fail rather than discard newer history. Workflow runs share a non-cancelling concurrency group. A deployment failure leaves its immutable snapshot retained for retry.

For a lifecycle-only change, use `scripts/package_review.py --catalog-only` against a checked-out copy of that catalog, with the required reason/replacement metadata. Such a change does not rewrite snapshot content; retain it on `pages-history` before the next build. No routine command deletes superseded or withdrawn snapshots.

## Manual workflow choices

- `examples`: flashlight, blue-dog, or both.
- `blue_dog_revision`: required exact model commit for blue-dog/both.
- `publish`: false builds and uploads the artifact; true also retains history and dispatches Pages deployment.

Pages must be configured to use GitHub Actions. The build job has read-only repository access. Only the publish job receives contents-write, Pages-write and OIDC permissions. Its deployment environment is `github-pages`.

Before a publishing run, the repository must contain the selected `LICENSE` and `THIRD_PARTY_NOTICES` files, and the browser packaging must retain the applicable dependency notices and source provenance. These files record the actual license decision; there is no additional repository-variable approval gate. The currently unresolved license choice is not resolved by adding this workflow.

CI installs Go 1.25.11, Node 22.14.0 and Python 3.12.10, checks out the exact native commit, runs `npm ci` against its lockfile, and installs its matching Python client. Python transitive dependencies currently follow that client's declared constraints; they are not a fully locked environment. Record the installed environment when investigating reproducibility differences. Native and viewer provenance plus asset hashes identify each resulting snapshot.

The configured checks include native specification validation, Python unit tests, Node DOM/navigation tests and the native renderer's TypeScript/unit checks. DOM tests do not replace rendered desktop/mobile review or the pending reader study. Successful pipeline execution would establish only the checks actually run.
